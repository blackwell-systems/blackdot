### H-1: `internal/shell` Package — Entire Package Unused in Production

**Severity:** High
**Check:** `dead_symbol`
**Files:** `/Users/dayna.blackwell/workspace/blackdot/internal/shell/shell.go`
**Confidence:** High [LSP unavailable — Grep fallback, reduced confidence]

The `internal/shell` package exports six symbols: `Detect`, `ExportVar`, `EvalOutput`, `SourceCommand`, `CommonIntegrations`, `GenerateFeatureCheck`, plus the `ShellType`, `ShellZsh`, `ShellBash`, `ShellFish`, `ShellUnknown` constants, and the `Integration` struct. The `internal/shell` package was presumably intended to be the canonical implementation for this functionality but was never wired in.

**Impact:** The entire `internal/shell` package is dead production code. Shell detection, export-var generation, integration hooks, and `GenerateFeatureCheck` are all unreachable from the CLI. Any bugs or improvements made to `internal/shell` have no production effect.

### M-1: Redundant `strings.ReplaceAll(name, "_", "_")` No-op

**Severity:** Medium
**Check:** `scope_analysis` / `silent_failure`
**File:** `/Users/dayna.blackwell/workspace/blackdot/internal/feature/registry.go:209`
**Confidence:** High [LSP unavailable — Grep fallback, reduced confidence]

In `checkEnvOverride`, the direct env-var name is computed as:

```go
directVar := "BLACKDOT_FEATURE_" + strings.ToUpper(strings.ReplaceAll(name, "_", "_"))
```

The `strings.ReplaceAll(name, "_", "_")` call replaces underscores with underscores — it is a no-op. The intent was almost certainly `strings.ReplaceAll(name, ".", "_")` (replacing dots with underscores, consistent with how `GetLayered` in `config.go:191` converts dot-notation keys to env-var format). This means a feature named with dots (e.g., a hypothetical `"aws.helpers"`) would not be found by its env-var override. For current feature names (all use underscores), the bug is latent but the dead ReplaceAll is a clear correctness signal.

**Impact:** For any feature name containing a dot, `BLACKDOT_FEATURE_<NAME>` env-var override silently fails to be constructed correctly. For current underscore-only names, behavior is coincidentally correct but the no-op is misleading and should be fixed regardless.

### M-4: Duplicate Blackdot-Dir Resolution — `getBlackdotDir()` vs `BlackdotDir()`

**Severity:** Medium
**Check:** `duplicate_semantics`
**Files:** `/Users/dayna.blackwell/workspace/blackdot/internal/cli/doctor.go:209`, `/Users/dayna.blackwell/workspace/blackdot/internal/cli/root.go:149`
**Confidence:** High [LSP unavailable — Grep fallback, reduced confidence]

Two separate functions resolve the blackdot directory with different logic:

`BlackdotDir()` in `root.go` (lines 149–151):
```go
func BlackdotDir() string {
    return blackdotDir  // populated by initConfig() via cobra.OnInitialize
}
```

`getBlackdotDir()` in `doctor.go` (lines 209–225):
```go
func getBlackdotDir() string {
    if dir := os.Getenv("BLACKDOT_DIR"); dir != "" { return dir }
    if _, err := os.Stat("/workspace/blackdot"); err == nil {
        // resolves symlinks
        return resolved
    }
    home, _ := os.UserHomeDir()
    if _, err := os.Stat(filepath.Join(home, ".blackdot")); err == nil {
        return filepath.Join(home, ".blackdot")
    }
    return ""
}
```

`getBlackdotDir()` additionally checks `/workspace/blackdot` (with symlink resolution) and returns `""` when the directory does not exist, while `BlackdotDir()` always returns `~/.blackdot` if `BLACKDOT_DIR` is unset. This means `doctor.go` uses a divergent, more conservative resolution path.

The duplicate also creates a maintenance hazard: changes to the canonical resolution in `root.go` will not propagate to `doctor.go`. `doctor.go` should call `BlackdotDir()` rather than maintaining its own resolver.

**Impact:** Inconsistent directory resolution between `doctor` and all other commands. Specific divergence: on machines where `~/.blackdot` does not exist (devcontainers, CI), doctor will return `""` and silently skip sections rather than using the configured `BLACKDOT_DIR`.

### M-5: Silently Ignored `json.Unmarshal` Error in `setInJSONFile`

**Severity:** Medium
**Check:** `error_wrapping`
**File:** `/Users/dayna.blackwell/workspace/blackdot/internal/cli/config.go:658`
**Confidence:** High [LSP unavailable — Grep fallback, reduced confidence]

In `setInJSONFile`:

```go
if data, err := os.ReadFile(path); err == nil {
    json.Unmarshal(data, &obj)   // error silently discarded
}
```

If the existing config file contains malformed JSON, `json.Unmarshal` returns a non-nil error that is completely discarded. The function proceeds with an empty `obj` map and overwrites the file with only the new key, silently destroying existing configuration. The project convention in `config.go` and other locations is to wrap and propagate all JSON errors.

**Impact:** A corrupted or manually-edited config file will be silently destroyed when `blackdot config set` is run. User data loss without any warning.

**Severity:** Low
**Check:** `silent_failure`
**File:** `/Users/dayna.blackwell/workspace/blackdot/internal/cli/backup.go:257`

### L-2: `init()` in `root.go` Contains Non-Trivial Setup

**Severity:** Low
**Check:** `init_side_effects`
**File:** `/Users/dayna.blackwell/workspace/blackdot/internal/cli/root.go:78`
**Confidence:** High [LSP unavailable — Grep fallback, reduced confidence]

```go
func init() {
    cobra.OnInitialize(initConfig)
    rootCmd.SetHelpFunc(customHelpFunc)
    rootCmd.PersistentFlags().BoolVarP(&verbose, "verbose", "v", false, "verbose output")
    rootCmd.PersistentFlags().BoolVar(&force, "force", false, "bypass feature checks")
    rootCmd.AddCommand(...)  // 22 subcommands
}
```

This `init()` registers global state (flags, help functions, all subcommands) at import time. The comment in the file notes "Do not call BlackdotDir() from package init() or during import," acknowledging the hazard. The Cobra pattern requires `init()` for command registration, so this is expected. However, all 22 `newXxxCmd()` constructors are called unconditionally at import time, not lazily.

This is a known pattern in Cobra-based CLIs and not a defect, but it means any `init()` side effects inside `newXxxCmd()` constructors (e.g., global variable initialization) run before `main()`. No such side effects are present currently.

**Severity is Low** because this is Cobra-idiomatic, but worth noting as a constraint for future command constructors.
